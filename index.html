☕ Core Java

1. Virtual Threads vs Platform Threads (Java 21)▶

Virtual threads are JVM-managed, cheap (KB stack), and mounted onto carrier platform threads. They shine for I/O-bound work — millions of in-flight HTTP calls instead of thousands. Do NOT use them for CPU-bound work or with synchronized blocks that pin the carrier.

❌ BAD — Thread pool starving on blocking I/O
// Fixed pool of 200 platform threads.
// 10,000 incoming requests → 9,800 queued.
ExecutorService pool = Executors.newFixedThreadPool(200);

for (Request r : requests) {
    pool.submit(() -> {
        // Each call blocks 300ms on a downstream API.
        String res = httpClient.get(r.url());
        save(res);
    });
}
// Throughput: ~666 req/s. CPU sits at 5%.
✅ GOOD — Virtual threads scale to millions
// One virtual thread per task. JVM mounts/unmounts on carriers.
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    for (Request r : requests) {
        exec.submit(() -> {
            // Blocking call unparks the VT; carrier picks up next task.
            String res = httpClient.get(r.url());
            save(res);
        });
    }
} // auto-close awaits all tasks
// Throughput: ~30,000 req/s on same hardware.
Gotcha: synchronized blocks pin the virtual thread to its carrier. Use ReentrantLock instead in hot paths.
2. Streams: lazy, parallel, and the boxing trap▶
❌ BAD — Boxing + parallel on small list
// Autoboxes every int to Integer.
// parallelStream() overhead dwarfs the work.
long sum = list.parallelStream()
    .map(x -> x * 2)
    .reduce(0, Integer::sum);

// Also: collect to a new list just to size it.
int n = items.stream()
    .filter(i -> i.active())
    .collect(Collectors.toList())
    .size();
✅ GOOD — Primitive stream, short-circuit count
// IntStream: no boxing, SIMD-friendly.
long sum = list.stream()
    .mapToInt(Integer::intValue)
    .map(x -> x * 2)
    .sum();

// Count directly — terminal op, no intermediate list.
long n = items.stream()
    .filter(Item::active)
    .count();
Rule of thumb: parallelStream only when N > 10,000 AND work per element > 1µs AND no shared mutable state.

4a. Java Memory Model — happens-before, volatile, false sharing▶

The JMM defines when one thread's writes become visible to another. Without proper synchronization, the JIT, CPU caches, and store buffers can reorder operations arbitrarily.

❌ BAD — Visibility bug, data race
class Worker {
    private boolean running = true;       // not volatile!

    public void run() {
        // JIT may hoist this read into a register.
        // Loop NEVER sees running=false even after stop().
        while (running) { doWork(); }
    }
    public void stop() { running = false; }
}
// Bug appears under -server JIT, not in dev.
✅ GOOD — volatile establishes happens-before
class Worker {
    private volatile boolean running = true;
    // volatile guarantees:
    //  1. Read sees the latest write from any thread
    //  2. No reordering across the volatile access
    //  3. Acts as a memory barrier
    public void run() { while (running) { doWork(); } }
    public void stop() { running = false; }
}
// For counters use AtomicInteger - volatile alone does NOT
// make i++ atomic (read-modify-write is 3 ops).

False sharing — invisible perf killer

❌ BAD — Adjacent fields → cache-line bouncing
class Counters {
    volatile long a;   // Same 64-byte cache line
    volatile long b;   // Different thread writes here
}
// Thread1 writes a, Thread2 writes b.
// Both invalidate each other's L1 cache → 10x slower.
✅ GOOD — @Contended (or padding)
// JVM flag: -XX:-RestrictContended
import jdk.internal.vm.annotation.Contended;

class Counters {
    @Contended volatile long a;
    @Contended volatile long b;
}
// JVM pads each field to its own cache line.
// LongAdder uses this internally for high-contention counters.

CountDownLatch ready = new CountDownLatch(workers);
CountDownLatch start = new CountDownLatch(1);
CountDownLatch done  = new CountDownLatch(workers);

for (int i = 0; i < workers; i++) {
    new Thread(() -> {

        runBenchmark();
        done.countDown();

}

// Semaphore as a connection pool
class ConnectionPool {
    private final Semaphore permits;
    private final BlockingQueue<Connection> pool;

    ConnectionPool(int size) {
        permits = new Semaphore(size, true);   // fair
        pool = new ArrayBlockingQueue<>(size);
        for (int i = 0; i < size; i++) pool.add(newConn());
    }
    Connection acquire() throws InterruptedException {
        permits.acquire();
        return pool.take();
    }
    void release(Connection c) {
        pool.offer(c);
        permits.release();
    }
}
4c. CompletableFuture — chains, combinators, exception handling▶
❌ BAD — Blocking get(), swallowed exceptions
CompletableFuture<User> uf = fetchUser(id);
CompletableFuture<Order> of = fetchOrders(id);

User u = uf.get();          // BLOCKS the calling thread
Order o = of.get();         // Defeats the point
return enrich(u, o);

// And: thenApply throws are silent without handle/exceptionally.
✅ GOOD — Compose with thenCombine + handle
CompletableFuture<Profile> profile = fetchUser(id)
    .thenCombineAsync(fetchOrders(id), this::enrich, executor)
    .orTimeout(2, TimeUnit.SECONDS)
    .handle((p, ex) -> {
        if (ex != null) {
            log.error("fetch failed", ex);
            return Profile.empty();        // fallback
        }
        return p;
    });
// Caller chains further or .join() at the EDGE only.

Cheat-sheet of CompletableFuture combinators

  • thenApply(fn) — transform result, sync
  • thenApplyAsync(fn, exec) — transform on different executor
  • thenCompose(fn) — flatMap for chained futures (avoids CF<CF<T>>)
  • thenCombine(other, biFn) — combine two unrelated futures
  • allOf(...) — wait for all; returns Void
  • anyOf(...) — return first one that completes
  • exceptionally(fn) — fallback on exception
  • handle((res, ex) → ...) — handle both success and error
  • whenComplete((res, ex) → ...) — side-effect only, doesn't change result
  • orTimeout(d, unit) — fail if not done in time
4d. ThreadLocal pitfalls + ScopedValue (Java 21+)▶

ThreadLocal on thread-pool threads is a classic memory leak: the value stays as long as the pool thread is alive. With virtual threads, ScopedValue is the modern replacement.

❌ BAD — ThreadLocal leak in thread pool
static final ThreadLocal<User> CURRENT = new ThreadLocal<>();

@GetMapping("/me")
public User me(@RequestHeader("X-User") String id) {
    CURRENT.set(loadUser(id));
    // ... work ...
    return CURRENT.get();
    // FORGOT to remove() — value leaks into next request
    // because Tomcat reuses worker threads.
}
✅ GOOD — ScopedValue (immutable, bounded)
// Java 21 preview, Java 23+ stable
final static ScopedValue<User> CURRENT = ScopedValue.newInstance();

public User handle(String id) {
    return ScopedValue.where(CURRENT, loadUser(id))
        .call(() -> {
            return CURRENT.get();      // visible to all callees
        });
    // Value is GC'd when the scope exits. No leak.
}

// Fallback for older Java: always pair set() with try/finally remove()
try {
    CURRENT.set(user);
    return doWork();
} finally {
    CURRENT.remove();
}
4e. Sealed classes + Records + Pattern Matching (Java 21)▶
// Algebraic data types in Java
sealed interface Result<T> permits Ok, Err {}
record Ok<T>(T value) implements Result<T> {}
record Err<T>(String message, Throwable cause) implements Result<T> {}

// Exhaustive switch - compiler errors if you add a new
// permitted subtype and forget to handle it
static <T> String describe(Result<T> r) {
    return switch (r) {
        case Ok<T>(var v)       -> "ok: " + v;
        case Err<T>(var m, var c) -> "err: " + m;
    };
}

// Records: immutable, equals/hashCode/toString free,
// compact constructors for validation
record Email(String address) {
    public Email {
        if (!address.contains("@"))
            throw new IllegalArgumentException("bad email");
        address = address.toLowerCase();      // canonicalize
    }
}
Why sealed + records win: Compile-time exhaustiveness on switch, no Visitor boilerplate, immutability by default. This is the "expressive Java" interviewers expect from senior candidates.
4f. NIO + Selector — non-blocking I/O without virtual threads▶

Pre-Java-21, NIO Selectors were the only way to handle thousands of connections per thread (Netty, Tomcat NIO connector are built on this). Even with virtual threads now, knowing Selector is interview-table-stakes for senior backend.

// Bare-bones echo server with Selector (1 thread, many clients)
public class EchoServer {
    public static void main(String[] args) throws IOException {
        Selector sel = Selector.open();
        ServerSocketChannel ssc = ServerSocketChannel.open();
        ssc.bind(new InetSocketAddress(8080));
        ssc.configureBlocking(false);
        ssc.register(sel, SelectionKey.OP_ACCEPT);

        ByteBuffer buf = ByteBuffer.allocate(1024);
        while (true) {
            sel.select();                    // blocks until any channel ready
            for (SelectionKey k : sel.selectedKeys()) {
                if (k.isAcceptable()) {
                    SocketChannel c = ssc.accept();
                    c.configureBlocking(false);
                    c.register(sel, SelectionKey.OP_READ);
                } else if (k.isReadable()) {
                    SocketChannel c = (SocketChannel) k.channel();
                    buf.clear();
                    int n = c.read(buf);
                    if (n == -1) { c.close(); continue; }
                    buf.flip();
                    c.write(buf);            // echo back
                }
            }
            sel.selectedKeys().clear();
        }
    }
}
When still relevant: Legacy services, embedded systems, anything below Java 21. With VTs you get the same scalability with regular blocking code — but you should be able to explain both models.
4g. JVM internals — TLAB, escape analysis, JIT, JFR profiling▶
  • TLAB (Thread-Local Allocation Buffer): Each thread has a slab of the Eden space. Object allocation is a pointer bump, no synchronization. This is why most allocation is <10ns.
  • Escape analysis: JIT proves an object never escapes a method → allocates on stack or scalar-replaces fields into registers. Result: zero heap pressure.
  • JIT compilation tiers: Tier 0 interpreted → Tier 1 C1 quick compile → Tier 4 C2 aggressive optimization. Hot methods reach Tier 4 after ~10K invocations.
  • Inlining: JIT replaces method calls with their body for small methods. Megamorphic call sites (3+ types) are NOT inlined — design with this in mind.
  • Deoptimization: If JIT assumptions break (new subclass loaded, type guard fails), JVM falls back to interpreter and may re-JIT.

JFR — Java Flight Recorder (built-in, free, production-safe)

# Start a 60-second recording while app runs
jcmd <pid> JFR.start name=profile duration=60s \
  filename=/tmp/profile.jfr settings=profile

# Or always-on with a fixed-size repository
java -XX:StartFlightRecording=disk=true,maxsize=1g,dumponexit=true,\
filename=/var/log/app.jfr -jar service.jar

# Analyze with JDK Mission Control (free GUI from Oracle)
jmc -open /tmp/profile.jfr
Production rule: Always enable JFR with a small overhead profile (~1%). When a prod issue hits, the recording is already there. No "we can't repro" — you have the data.

🌱 Spring Boot 3.x

4. @Transactional propagation pitfalls▶

Self-invocation does not pass through the proxy. REQUIRES_NEW on the same bean's method from itself = no new transaction. This silently corrupts data.

❌ BAD — Self-invocation, propagation ignored
@Service
public class OrderService {

    @Transactional
    public void placeOrder(Order o) {
        save(o);
        audit(o); // self call - proxy bypassed!
    }

    @Transactional(propagation = REQUIRES_NEW)
    public void audit(Order o) {
        // Will join the outer TX, not start a new one.
        auditRepo.save(toAudit(o));
    }
}
✅ GOOD — Separate bean OR self-injection
@Service
public class OrderService {

    private final AuditService auditService; // separate bean

    @Transactional
    public void placeOrder(Order o) {
        save(o);
        auditService.audit(o); // through proxy, NEW TX honored
    }
}

@Service
public class AuditService {
    @Transactional(propagation = REQUIRES_NEW)
    public void audit(Order o) { auditRepo.save(toAudit(o)); }
}
Other landmines: private/final methods on a proxied bean are not advised. Checked exceptions don't roll back by default — set rollbackFor = Exception.class if you throw them.
5. Spring Security: JWT + OAuth2 Resource Server▶
❌ BAD — Hand-rolled JWT filter, HS256 secret
// Symmetric secret stored in application.yml. Anyone with the
// secret can forge tokens. Custom filter misses edge cases:
// no clock skew, no kid rotation, no audience check.
@Component
public class MyJwtFilter extends OncePerRequestFilter {
    @Value("${jwt.secret}") String secret;
    protected void doFilterInternal(...) {
        String token = req.getHeader("Authorization").substring(7);
        Claims c = Jwts.parser().setSigningKey(secret)
                       .parseClaimsJws(token).getBody();
        // ... set auth context
    }
}
✅ GOOD — Resource Server, RS256 via JWKS
@Configuration
@EnableWebSecurity
public class SecurityConfig {

  @Bean
  SecurityFilterChain chain(HttpSecurity http) throws Exception {
    http
      .authorizeHttpRequests(a -> a
        .requestMatchers("/api/admin/**").hasRole("ADMIN")
        .anyRequest().authenticated())
      .oauth2ResourceServer(o -> o.jwt(j -> j
        .jwkSetUri("https://idp.example.com/.well-known/jwks.json")
        .jwtAuthenticationConverter(rolesConverter())))
      .csrf(c -> c.disable())
      .sessionManagement(s -> s.sessionCreationPolicy(STATELESS));
    return http.build();
  }
}

❌ BAD — Field injection, mutable, hidden deps

7. Isolates for heavy compute (don't block the UI thread)▶
❌ BAD — Parsing 5MB JSON on UI isolate
Future<List<Item>> load() async {
  final res = await http.get(url);
  // jsonDecode + mapping blocks the UI for 800ms.
  final raw = jsonDecode(res.body) as List;
  return raw.map((j) => Item.fromJson(j)).toList();
}
✅ GOOD — Offload to isolate via compute()
List<Item> _parse(String body) {
  final raw = jsonDecode(body) as List;
  return raw.map((j) => Item.fromJson(j)).toList();
}

Future<List<Item>> load() async {
  final res = await http.get(url);
  return compute(_parse, res.body); // runs on separate isolate
}

❌ BAD — Whole tree rebuilds on every tick

9. Bloc lifecycle + Cubit + BlocObserver▶

Bloc = events → states. Cubit = simpler, methods → states (no events). Use Cubit unless you need replayable event history or transformer-based debouncing of events.

❌ BAD — setState chaos, no separation
class _UserPageState extends State<UserPage> {
  bool loading = false;
  User? user; String? error;

  Future<void> load() async {
    setState(() => loading = true);
    try {
      user = await api.fetchUser();
    } catch (e) { error = e.toString(); }
    setState(() => loading = false);
  }
  // No way to unit test. Reaching for a Bloc only after pain.
}
✅ GOOD — Cubit with sealed states
sealed class UserState {}
class UserInitial extends UserState {}
class UserLoading extends UserState {}
class UserLoaded extends UserState { final User user; UserLoaded(this.user); }
class UserError extends UserState { final String msg; UserError(this.msg); }

class UserCubit extends Cubit<UserState> {
  final UserRepo repo;
  UserCubit(this.repo) : super(UserInitial());

  Future<void> load() async {
    emit(UserLoading());
    try {
      final u = await repo.me();
      emit(UserLoaded(u));
    } catch (e) {
      emit(UserError(e.toString()));
    }
  }
}

// In widget:
BlocBuilder<UserCubit, UserState>(
  builder: (ctx, s) => switch (s) {
    UserLoading() => const CircularProgressIndicator(),
    UserLoaded(:final user) => Text(user.name),
    UserError(:final msg) => Text('Error: $msg'),
    _ => const SizedBox.shrink(),
  },
);

BlocObserver — global lifecycle logging

class AppBlocObserver extends BlocObserver {
  @override
  void onChange(BlocBase bloc, Change change) {
    debugPrint('${bloc.runtimeType}: ${change.currentState} → ${change.nextState}');
    super.onChange(bloc, change);
  }
  @override
  void onError(BlocBase bloc, Object error, StackTrace st) {
    FirebaseCrashlytics.instance.recordError(error, st);
    super.onError(bloc, error, st);
  }
}

void main() {
  Bloc.observer = AppBlocObserver();
  runApp(const App());
}
Rule of thumb: One Bloc/Cubit per feature, scoped via BlocProvider. Never put Blocs in global singletons — you lose proper disposal.
10. Stream transformers — debounce, switchMap, distinct (interview gold)▶

Bloc lets you register an event transformer that controls event scheduling: droppable, restartable, sequential, concurrent. Combined with rxdart operators on streams, this is what separates senior from intern.

❌ BAD — Every keystroke fires an HTTP call
class SearchBloc extends Bloc<SearchEvent, SearchState> {
  SearchBloc(this.repo) : super(SearchInitial()) {
    on<SearchQueryChanged>((e, emit) async {
      // Types "f", "fl", "flu", "flut" → 4 racing HTTP calls.
      // Older response can overwrite newer.
      emit(SearchLoading());
      final r = await repo.search(e.q);
      emit(SearchLoaded(r));
    });
  }
}
✅ GOOD — Debounce + switchMap (restartable)
import 'package:bloc_concurrency/bloc_concurrency.dart';
import 'package:stream_transform/stream_transform.dart';

EventTransformer<E> debounceRestartable<E>(Duration d) {
  return (events, mapper) => restartable<E>().call(
    events.debounce(d), mapper);
}

class SearchBloc extends Bloc<SearchEvent, SearchState> {
  SearchBloc(this.repo) : super(SearchInitial()) {
    on<SearchQueryChanged>(
      (e, emit) async {
        if (e.q.trim().length < 2) {
          emit(SearchInitial()); return;
        }
        emit(SearchLoading());
        final r = await repo.search(e.q);
        emit(SearchLoaded(r));
      },
      transformer: debounceRestartable(
        const Duration(milliseconds: 300)),
    );
  }
}
// 300ms after last keystroke → 1 call. New keystroke
// cancels in-flight call. Only newest result emits.

The four bloc_concurrency transformers

TransformerBehaviorUse case
concurrent() (default)All events processed in parallelIndependent fire-and-forget
sequential()Events queued, one at a timeCart updates, deposits
droppable()New events dropped if one runningSubmit-once buttons
restartable()Cancel previous, run newSearch, type-ahead

rxdart stream operators worth memorizing

// Combine multiple streams into one state
Rx.combineLatest2(authStream, profileStream,
    (auth, profile) => SessionState(auth, profile));

// distinct() avoids re-emitting same state
cubit.stream.distinct().listen(...);

// throttleTime - emit first then ignore for N ms (rate-limit)
buttonClicks.throttleTime(Duration(seconds: 1));

// switchMap - cancel previous inner stream when outer fires
queryStream.switchMap((q) => repo.searchStream(q));
11. WebSockets — connect, reconnect with backoff, heartbeat▶

Production WebSocket code is never WebSocket.connect() and you're done. You need: auto-reconnect with exponential backoff + jitter, heartbeat ping/pong, queueing while disconnected, JWT refresh on 401, lifecycle disposal.

❌ BAD — Connect once, hope nothing breaks
class ChatService {
  late WebSocketChannel ch;
  ChatService(String url) {
    ch = WebSocketChannel.connect(Uri.parse(url));
    // No reconnect, no auth, no error handling.
    // App backgrounds → socket dies silently.
    ch.stream.listen((msg) => print(msg));
  }
  void send(String m) => ch.sink.add(m);
}
✅ GOOD — Reconnecting socket with backoff
class ReconnectingWebSocket {
  final Uri url;
  final Future<String> Function() tokenProvider;
  final _controller = StreamController<String>.broadcast();
  WebSocketChannel? _ch;
  StreamSubscription? _sub;
  Timer? _hb, _reconnect;
  int _attempt = 0;
  bool _disposed = false;
  final _queue = <String>[];

  ReconnectingWebSocket(this.url, this.tokenProvider);
  Stream<String> get stream => _controller.stream;

  Future<void> connect() async {
    if (_disposed) return;
    try {
      final token = await tokenProvider();
      _ch = WebSocketChannel.connect(url,
        protocols: ['v1.chat', 'jwt.$token']);
      _attempt = 0;
      _flushQueue();
      _startHeartbeat();
      _sub = _ch!.stream.listen(
        (msg) => _controller.add(msg as String),
        onError: (e) => _scheduleReconnect(),
        onDone: _scheduleReconnect,
        cancelOnError: true,
      );
    } catch (_) { _scheduleReconnect(); }
  }

  void send(String msg) {
    if (_ch != null) {
      _ch!.sink.add(msg);
    } else {
      _queue.add(msg);              // queue for next connect
    }
  }
  void _flushQueue() {
    for (final m in _queue) _ch!.sink.add(m);
    _queue.clear();
  }
  void _startHeartbeat() {
    _hb?.cancel();
    _hb = Timer.periodic(const Duration(seconds: 25),
      (_) => _ch?.sink.add('{"op":"ping"}'));
  }
  void _scheduleReconnect() {
    _ch = null; _sub?.cancel(); _hb?.cancel();
    if (_disposed) return;
    // Exponential backoff with jitter, capped 30s
    final delay = math.min(30, math.pow(2, _attempt++).toInt())
                + math.Random().nextInt(1000) ~/ 1000;
    _reconnect = Timer(Duration(seconds: delay), connect);
  }
  Future<void> dispose() async {
    _disposed = true;
    _hb?.cancel(); _reconnect?.cancel();
    await _sub?.cancel();
    await _ch?.sink.close(1000);
    await _controller.close();
  }
}

12. Isolates — Isolate.spawn, SendPort, long-lived workers▶

compute() is for one-shot. For repeated heavy work (image processing, search, parsing), spawn a long-lived isolate with two-way communication.

// Worker isolate that accepts jobs forever
void _worker(SendPort sendPort) {
  final receivePort = ReceivePort();
  sendPort.send(receivePort.sendPort);    // give main our port

  receivePort.listen((msg) {
    if (msg is _Job) {
      // Heavy compute — runs in own isolate, own heap
      final result = _heavyParse(msg.payload);
      msg.reply.send(result);
    } else if (msg == 'shutdown') {
      receivePort.close();
      Isolate.exit();
    }
  });
}

class WorkerPool {
  late Isolate _isolate;
  late SendPort _commands;
  final _ready = Completer<void>();

  Future<void> start() async {
    final init = ReceivePort();
    _isolate = await Isolate.spawn(_worker, init.sendPort);
    _commands = await init.first as SendPort;
    _ready.complete();
  }

  Future<R> submit<R>(dynamic payload) async {
    await _ready.future;
    final reply = ReceivePort();
    _commands.send(_Job(payload, reply.sendPort));
    return await reply.first as R;
  }

  void dispose() {
    _commands.send('shutdown');
    _isolate.kill(priority: Isolate.beforeNextEvent);
  }
}
class _Job { final dynamic payload; final SendPort reply;
  _Job(this.payload, this.reply); }
Memory boundary: Isolates do NOT share memory. Every send() serializes via SnapshotKind.full — large objects copy fully. Pass primitives or TypedData (Uint8List etc.) for efficiency.

15. CustomPainter and RenderObject — pixel-level control▶
// Draw a gauge from scratch
class GaugePainter extends CustomPainter {
  final double progress;     // 0..1
  GaugePainter(this.progress);

  @override
  void paint(Canvas canvas, Size size) {
    final center = size.center(Offset.zero);
    final radius = size.shortestSide / 2 - 8;

    // Background arc
    final bg = Paint()
      ..color = Colors.grey.shade800
      ..style = PaintingStyle.stroke
      ..strokeWidth = 12;
    canvas.drawArc(
      Rect.fromCircle(center: center, radius: radius),
      math.pi * 0.75, math.pi * 1.5, false, bg);

    // Progress arc with gradient
    final fg = Paint()
      ..shader = SweepGradient(
        startAngle: math.pi * 0.75,
        endAngle: math.pi * 2.25,
        colors: const [Colors.green, Colors.amber, Colors.red],
      ).createShader(Rect.fromCircle(center: center, radius: radius))
      ..style = PaintingStyle.stroke
      ..strokeCap = StrokeCap.round
      ..strokeWidth = 12;
    canvas.drawArc(
      Rect.fromCircle(center: center, radius: radius),
      math.pi * 0.75, math.pi * 1.5 * progress, false, fg);

    // Center text
    final tp = TextPainter(
      text: TextSpan(text: '${(progress * 100).toInt()}%',
        style: const TextStyle(fontSize: 32, fontWeight: FontWeight.bold)),
      textDirection: TextDirection.ltr)..layout();
    tp.paint(canvas, center - Offset(tp.width / 2, tp.height / 2));
  }

  @override
  bool shouldRepaint(GaugePainter old) => old.progress != progress;
}

20. Native interop — FFI for C/C++, Method Channels for Kotlin/Swift▶

Need to call a C library (image SDK, crypto, ML model)? Use dart:ffi — zero overhead, direct memory access. Method Channels are for OS APIs that need Kotlin/Swift; FFI is for portable native code.

// native.c
// int32_t add(int32_t a, int32_t b) { return a + b; }
// Build as libnative.so / native.dylib / native.dll

import 'dart:ffi';
import 'dart:io';
import 'package:ffi/ffi.dart';

typedef AddDart = int Function(int, int);          // Dart signature

class NativeMath {
  static final DynamicLibrary _lib = Platform.isAndroid
    ? DynamicLibrary.open('libnative.so')
    : DynamicLibrary.process();

  static final AddDart add = _lib
    .lookup<NativeFunction<_AddC>>('add')
    .asFunction();
}

void main() {
  print(NativeMath.add(3, 4));   // 7, no copy, no isolate
}

1. URL Shortener — bit.ly clone (10B URLs, 1000:1 read:write)▶

Scale estimate

100M new URLs/month → 40 writes/sec avg, 400 peak. 100B reads/month → 40K reads/sec. Storage: 100M × 12 months × 5 years × 500 bytes ≈ 3 TB. Bandwidth: 40K × 500B = 20 MB/s egress.

API

POST /shorten { longUrl, customAlias?, ttl? } -> { shortUrl, expiresAt }
GET  /{shortCode} -> 301 redirect

Key choice: hash vs counter-based short code

Counter (base62 of monotonic ID from Snowflake/Sonyflake) → no collisions, predictable. MD5(url) first 7 chars → collisions possible, needs retry. Pick counter-based.

Architecture

┌────────────────┐ Browser ───────────► │ CloudFront │ (cache hot URLs, 30d TTL) └───────┬────────┘ │ miss ┌───────▼────────┐ │ API Gateway │ (WAF + rate limit) └───────┬────────┘ │ ┌───────────────────┼───────────────────┐ │ │ │ ┌─────▼─────┐ ┌─────▼─────┐ ┌─────▼─────┐ │ Lambda │ │ Lambda │ │ Lambda │ │ Shorten │ │ Resolve │ │ Analytics │ └─────┬─────┘ └─────┬─────┘ └─────┬─────┘ │ │ │ │ writeID via │ GetItem │ Async event │ Snowflake gen │ │ ▼ ▼ ▼ ┌──────────────────────────────┐ ┌──────────┐ │ DynamoDB (url_map) │ │ Kinesis │──► S3 → Athena │ PK = shortCode GSI = userId│ └──────────┘ └──────────────────────────────┘

Why DynamoDB and not RDS

Single-key lookup at 40K rps. DynamoDB auto-scales, no read replica lag, <10ms p99. RDS would need sharding by short-code prefix and managing replicas.

Caching strategy

CloudFront edge cache for hot URLs (Pareto: top 5% URLs = 80% of clicks). Cache-Control max-age=86400 for permanent URLs. Cache miss → Lambda → DynamoDB.

2. Distributed Rate Limiter — Token Bucket on Redis▶

Algorithm choice

Token bucket = burst-friendly, smooth long-run rate. Sliding window log = exact, memory-heavy. Fixed window = simple, boundary spikes. Pick token bucket for APIs.

Architecture

Client ──► API Gateway (per-API key throttle: 1st line) │ ▼ ┌─────────────────┐ ┌──────────────────────┐ │ ALB / Service │ ──────► │ Redis Cluster │ │ (Lua eval atom)│ │ HSET buckets:<uid> │ └─────────────────┘ │ tokens, ts │ │ └──────────────────────┘ ▼ allow / 429 Backend Lua script (atomic, single round-trip): 1. now = TIME 2. tokens = HGET bucket:uid tokens 3. last = HGET bucket:uid ts 4. add = (now - last) * rate 5. tokens = min(capacity, tokens + add) 6. if tokens >= 1: tokens-- ; ALLOW 7. else: DENY (return retry-after) 8. HSET back

Why Lua / EVAL

Atomicity without a transaction. Two clients reading then writing would race. EVAL runs single-threaded on the Redis shard owning the key.

CAP positioning

Redis cluster is AP with replication. A failover may lose 1-2 seconds of token state — acceptable for rate limiting (worst case: client gets free burst). For payments throttling, use Redis with WAIT + AOF fsync=always.

5. Distributed Job Scheduler — SQS + Lambda SnapStart + RDS▶

Architecture

┌──────────────────────┐ │ Submission API │── INSERT ──► RDS (jobs table) │ (Fargate/ECS) │ status=PENDING └──────────────────────┘ run_at=ts │ │ poll every 10s ▼ ┌───────────────────────────┐ │ Dispatcher (EventBridge │ │ rule, 10-sec cron) │ │ SELECT due jobs ─► SQS │ └────────────┬──────────────┘ │ ┌────────────▼─────────────┐ │ SQS (with visibility │ │ timeout = job SLA) │ │ + DLQ after 3 attempts │ └────────────┬─────────────┘ │ ┌──────────────────┼────────────────┐ ▼ ▼ ▼ ┌─────────────┐ ┌─────────────┐ ┌─────────────┐ │ Lambda │ │ Lambda │ │ Lambda │ │ SnapStart │ │ SnapStart │ │ SnapStart │ │ worker │ │ worker │ worker └──────┬──────┘ └──────┬──────┘ └──────┬──────┘ └──────┬───────────┴────────────────┘ ▼ RDS: UPDATE status, attempt_count

Why SnapStart

Lambda cold start for JVM ≈ 2-3s. SnapStart snapshots a warm JVM after init, restores in <200ms. Critical for spiky job dispatch.

Exactly-once delivery

SQS is at-least-once. Use idempotency: UPDATE jobs SET status='RUNNING' WHERE id=? AND status='PENDING' with optimistic lock. If rows-affected = 0, another worker grabbed it — exit.

Consistent hashing usage

For sticky job-to-worker routing (e.g., per-tenant rate limit), hash jobId into a ring of N workers. Adding workers reshuffles ~1/N keys, not all.

🎯 Cross-cutting Concepts

CAP Theorem

  • CP: RDS, MongoDB (writeConcern=majority), HBase
  • AP: Cassandra, DynamoDB (default), Riak
  • Partition will happen → pick C or A. You cannot have both during a partition.

Consistent Hashing

  • Place nodes on a ring [0, 2³²)
  • Each key hashed → next clockwise node
  • Add node: only K/N keys move
  • Virtual nodes (~150/server) → uniform load

CDC (Change Data Capture)

  • Debezium reads DB binlog
  • → Kafka topic per table
  • Downstream: cache invalidation, search index, analytics
  • No dual-write inconsistency

Kafka vs SQS vs SNS

  • Kafka: ordered, replayable, multi-consumer, high throughput
  • SQS: single consumer group, at-least-once, simple
  • SNS: pub/sub fanout, no persistence beyond retry
